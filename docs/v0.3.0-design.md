# humanoid_parkour v0.3.0 — advanced parkour design

**Status: design for review. No code written against this yet.**

v0.2.0 is a correct, released, signed *port* of a task that is too small to be interesting. This
document says what to change to make it real parkour, in dependency order, with the costs named.

## 1. What is wrong with v0.2.0 (the case for a redesign, not a tweak)

| Parkour implies | v0.2.0 actually does | Where |
|---|---|---|
| Elevation | **Flat plane.** One `type="plane"` geom. | `env/assets_humanoid.xml:25` |
| Stairs, jumps, gaps | None. Solid boxes to step over. | `env/course.py:69-84` |
| Varied surfaces | **One friction value globally** (`1 .1 .1` on floor *and* hurdles). | `assets_humanoid.xml:25`, `course.py:81` |
| Route choice | None. Hurdles span `TRACK_HALF_WIDTH + 0.5`, deliberately un-clippable → the task is strictly 1-D. | `course.py:80` |
| Obstacle scale | Tallest "hard" hurdle **0.35 m** vs a torso starting at **1.4 m** — shin height. | `course.py:32` |
| Task diversity | 3 tiers varying only `(n, height, gap)`. | `course.py:29-33` |

The baseline completing only ~17% of courses makes this *look* hard. It isn't — that is a weak
baseline (110M-step PPO on a torque-limited humanoid) on a narrow task. Low baseline score ≠ rich
problem. It is actively harmful: the completion/fall coin-flip is what drives σ_round to 21× the
sizing criterion (HANDOFF §4, open item 1).

## 2. Is the robot right? (decide this first — everything else depends on it)

The stock Gymnasium humanoid has `ctrlrange ±0.4` with `gear` up to 300 and is a well-known
hard-to-train, weakly-actuated model. It can be coaxed into a shambling run; **jumping a gap or
climbing a 0.2 m stair is at or beyond its actuation envelope.** If we build stairs and gaps on
top of this robot, the likely outcome is a competition nobody can score on — the failure mode that
makes a leaderboard pure noise.

**Recommendation: switch to a realistic humanoid from `mujoco_menagerie`** — Unitree **G1** (23
DoF) or **H1** (19 DoF). They ship calibrated actuator models, sensible joint limits, and there is
published locomotion/parkour work on both to prove the task is learnable.

Costs, stated plainly: it changes `OBS_DIM`/`ACT_DIM`, **invalidates `baseline/baseline.onnx`
entirely**, and requires retraining from scratch. It also adds a vendoring + licence-review step
(Menagerie models are individually licensed; G1/H1 are BSD-3 but confirm before shipping).

*Alternative if we must keep the current robot:* cap obstacles at what it can physically clear
(≈0.25 m steps, no gaps) and accept that "parkour" means "hurdles and stairs". Honest, but it
concedes most of what you asked for.

## 3. Terrain generator

Replace `generate_course` with a **segment composer**: a course is an ordered list of segments,
each with its own geometry and a hidden friction value. Total length ~40 m (from 20 m).

Segment classes:

| Class | Parameters | What it tests |
|---|---|---|
| `flat` | length | run-up, recovery |
| `hurdle` | height 0.10–0.45, depth | existing step-over |
| `stairs_up` / `stairs_down` | n steps 3–8, rise 0.08–0.22, run 0.25–0.40 | foot placement, descent control (descent is *harder* and usually skipped) |
| `gap` | width 0.3–1.1 | jumping, takeoff/landing timing |
| `ramp` | angle ±8–20° | slope adaptation |
| `stepping_stones` | n, lateral offset ±0.5, spacing | **precise foot placement + lateral route choice — this is what breaks the 1-D-ness** |
| `beam` | width 0.3–0.6, length | lateral balance |
| `rubble` | amplitude 0.02–0.08 | robustness to unmodelled ground |
| `slick` | friction 0.15–0.35 (geometry identical to `flat`) | the hidden-variable probe |

**Geometry representation: composited box geoms, not an `hfield`.** Boxes give exact stair edges
and let us compute the height scan *analytically* from the segment list — no raycasting. That
matters for determinism: an analytic height lookup cannot drift with MuJoCo collision internals,
and we already have a determinism budget problem. `rubble` is the one exception and can use a small
`hfield` patch.

**Gaps require raising the course.** A gap has to be a real void, so the whole track sits on a
plinth (base top at z ≈ 0.6 m) and falling into a gap becomes a new terminal reason `fell_off`.

## 4. Observation — geometry visible, friction hidden

Per your call: **the policy sees terrain geometry but must infer surface properties.** That makes
this an adaptation problem, not just a control problem, and it is what forces memory (§5).

| Block | Dims | Notes |
|---|---|---|
| projected gravity | 3 | replaces the raw quaternion — no sign ambiguity, standard practice |
| base height above local terrain | 1 | *local*, not absolute z — the only way this generalizes over elevation |
| joint positions | `nq_j` | |
| joint velocities | `nq_j` | |
| base linear velocity | 3 | |
| base angular velocity | 3 | |
| previous action | `nu` | standard; gives implicit dynamics feedback |
| foot contact flags | 2–4 | proprioceptive, and the main channel for inferring friction |
| **height scan** | **77** | 11 (x) × 7 (y) grid in the base yaw frame, x ∈ [−0.5, 2.5] m, y ∈ [−0.6, 0.6] m, values = `base_z − terrain_height` |
| task | 2 | fraction of course remaining, lateral offset from centerline |

≈ 140–190 dims depending on robot. **Explicitly absent: friction, segment class labels, segment
parameters, the course seed.** The height scan is the *only* exteroception, which is exactly the
`legged_gym`/ANYmal formulation that made blind→perceptive locomotion work.

Note this also fixes an S1-class leak properly: with geometry delivered as a scan, there is no
reason to ever send a seed or an index into the player sandbox.

## 5. Submission contract — keep ONNX, allow recurrence

**ONNX stays.** SB3 is a *training* framework, not a submission format; its native artifact is a
pickle `.zip`, i.e. arbitrary code execution at load. Accepting those would move us from the top
of the skill's format ladder to the bottom and require a Layer-2 screen we currently don't need.
Miners can train in SB3, JAX, Tinker, anything — only the graph is submitted, exactly as
`baseline/train_baseline.py` already does via `ExportablePolicy`.

**But the current fixed `[1,56] → [1,17]` interface forbids memory**, and hidden friction makes
memory close to mandatory. New contract — accept **either** shape:

```
feed-forward:  obs [batch, OBS_DIM]                     -> action [batch, ACT_DIM]
recurrent:     obs [batch, OBS_DIM], h_in [batch, H]    -> action [batch, ACT_DIM], h_out [batch, H]
```

`H` is declared in the spec (suggest 128). The player wrapper zeroes `h` on `reset()` and feeds
`h_out` back each step; a feed-forward graph simply omits both. One interface, recurrence optional,
and `reset()` stops being a no-op — which also means the wrapper finally has per-episode state,
so `reset()` must clear it or scores leak across courses.

## 6. Fixing the wall-clock blocker — batch the observations

This is the prerequisite for everything above, because richer terrain makes it worse. v0.2.0 makes
`N × steps` ≈ 108,000 sequential `/act` calls inside `referee.timeout_s: 900` — ~8 ms per call
against a permitted `deadline_ms: 500` (open item 3). A 40 m course at ~1800 steps would be far
worse.

**Run all courses in lockstep and batch the observations.** Instead of one course at a time, step
every still-active course together and send one `/act` per timestep with a `[K, OBS_DIM]` batch.
HTTP round-trips drop from `N × steps` to `steps` — a ~120× reduction, removing minutes of pure
protocol overhead. Memory is fine: ~120 small `MjModel`/`MjData` pairs is tens of MB inside 1.5Gi.

**Determinism caveat that decides the implementation:** batched matmul and single-row matmul do not
produce identical floats, and the active set shrinks as courses terminate, so batch width varies
during an episode. To keep "same policy → same score" independent of *how many* courses happen to
be alive, **the player wrapper must loop over the batch rows internally** and run the graph one row
at a time. We take the HTTP amortization and refuse the numerical variability. This also means a
miner's fixed-batch-1 export keeps working.

This change is worth landing in v0.2.x on its own, independent of the redesign.

## 7. Scoring — checkpoints, and why they also fix the σ problem

Keep the shape (completion beats non-completion; faster completion beats slower; partial progress
pays), but make progress **checkpoint-based**: ~20 checkpoints along the course, score credits
checkpoints reached plus a time bonus on completion.

The reason is not cosmetic. σ_round is 21× the criterion because the current score is nearly
**bimodal** — a course either completes (≈1.0–2.0) or falls (≈0.0–0.3), so one coin-flip moves the
mean a lot. A 20-checkpoint score is far smoother, which **directly attacks open item 1** rather
than arguing around it. Combined with stratifying N across segment classes, this is the most
plausible route to actually passing the sizing criterion instead of asking the platform to re-score
incumbents.

Progress stays monotone in x (it is still a track), so the metric cannot be gamed by looping.

## 8. Gates, revised

- `fell`: the v0.2.0 legs-only rule (**any** non-foot geom touching the floor) is **wrong for real
  parkour** — a hand on a wall is legitimate. Replace with: torso below a terrain-relative height,
  or a non-foot geom contacting the ground *plane* — while allowing hand contact with obstacle
  geoms. This needs a written call on whether vaulting is in the spirit of the goal (§1 currently
  says legs only; real parkour says otherwise).
- `fell_off`: new — fell into a gap or off the plinth.
- `physics_glitch`: tighten `|qvel| > 100` drastically. It is ~30× the baseline's 3.5 m/s and does
  not bound superhuman speed at all (open item 4). Propose a per-body-part limit tied to plausible
  dynamics, and **reorder the checks so `fell`/`out_of_bounds` are evaluated before `completed`** —
  today a ballistic body crossing the line while falling scores a full completion.
- `out_of_bounds`: must widen for `stepping_stones` lateral offsets.

## 9. Baseline feasibility — the real risk

Hidden friction + stairs + gaps on a 20-ish-DoF humanoid is a genuinely hard RL problem. Published
parkour results use ~1e9–1e10 environment steps with massively parallel GPU simulation. **CPU
MuJoCo + SB3 will not get there** — the v0.2.0 baseline took ~110M steps and still falls on 83% of
a much easier task.

- Train the baseline with **MJX (MuJoCo XLA) on GPU**, with a curriculum over segment classes and
  domain randomization over friction.
- Evaluation stays `process_type: cpu` — the referee only steps physics. GPU is a *baseline
  training* cost, off-platform, and does not change the spec.
- Keep the `easy` tier close to v0.2.0's difficulty so the baseline scores well above 0 and miners
  have a climbable gradient. If the baseline can't clear the easy tier, the competition is noise.
- Miner compute cost rises a lot, which interacts with the ≈$1 fee and the 5-day reveal — worth
  revisiting both.

## 10. Order of work

1. Land the batched-lockstep referee (§6) on v0.2.x — independent, unblocks everything.
2. Decide the robot (§2). Blocks all dimensioning.
3. Terrain composer + analytic height scan (§3, §4), with a rendering script for visual review.
4. New submission contract + player wrapper (§5).
5. Checkpoint scoring + revised gates (§7, §8), then re-measure σ_round — this is the number that
   decides whether the design is sound.
6. Baseline training on MJX (§9); iterate difficulty until the easy tier is comfortably solvable.
7. Re-run the sizing procedure, rewrite HANDOFF §4, release v0.3.0.

## 11. Open decisions for you

1. **Robot**: switch to G1/H1, or stay on the Gymnasium humanoid and cap difficulty to its envelope?
2. **Vaulting**: is hand contact with obstacles allowed? §1's goal statement currently forbids it;
   real parkour allows it. This changes the fall gate and the success statement.
3. **Gap-jumping via plinth**: accept the added complexity (and the new `fell_off` reason), or drop
   gaps and keep the course ground-level?
4. **σ target**: do we commit to actually passing `σ ≤ margin/4` via checkpoint scoring, or do we
   keep asking the platform to re-score incumbents each round?
